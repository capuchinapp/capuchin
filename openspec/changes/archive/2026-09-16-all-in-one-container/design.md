## Context

На данный момент приложение деплоится как два образа и контейнера: бэкенд (`build/Dockerfile_back`, Go, port 3000) и фронтенд (`build/Dockerfile_front`, nginx, port 80). `deploy/compose.yaml` публикует два хостовых порта (3001→3000 API, 3002→80 статика), а внешний `deploy/nginx_capuchin.conf` проксирует `/api` на 3001 и всё остальное на 3002. Фронтенд в production уже ходит в API по same-origin `/api` — см. `front/src/services/Api.js` (`getBaseUrl()` возвращает `${location.protocol}//${location.host}/api`); ветка `port - 1` используется только для localhost-разработки на двух портах. Мотивация изменения — в `proposal.md`.

Ограничения текущего состояния:
- Хранилище — SQLite, допускает только один пишущий процесс → blue-green deployment опасен.
- Приложение — Fiber; порт задаётся `HTTP_PORT` (default 3000), метрики отдельно на `METRICS_PORT` (default 8080).
- `docker compose up` применяет миграции goose перед стартом приложения и монтирует `./data:/app/data`.

## Goals / Non-Goals

**Goals:**
- Один all-in-one Docker-образ и один контейнер, обслуживающий API и статику фронтенда на одном порту (3000).
- Раздача статики фронтенда Go-приложением через embed FS; отдельный nginx-контейнер не требуется.
- Билд фронтенда (bun + vite) как промежуточный шаг multi-stage сборки.
- Сохранение данных SQLite на томе, применимость миграций goose, работающий healthcheck.
- Актуальные README, nginx-конфиг и CI/CD без blue-green и без двух портов.

**Non-Goals:**
- Изменение доменной логики приложения, API-контрактов и формата данных.
- Изменение `METRICS_PORT` (метрики остаются внутренним портом, наружу не публикуются).
- Управление TLS на уровне приложения: TLS по-прежнему терминирует внешний nginx-прокси.

## Decisions

### 1. Раздача статики через go:embed + Fiber

Фронтенд собирается в `front/dist`, затем внутри Docker-сборки копируется в пакет `back/internal/application/cloudbackend/web/dist`, и только после этого собирается Go-бинарник — embed подхватывает файлы на этапе компиляции. В репозиторий кладётся файл-заглушка `web/dist/.gitkeep`, чтобы `go build` работал и вне Docker (go:embed требует хотя бы один файл в каталоге).

Регистрация в fiber:
1. Группа `/api` объявляется как сейчас (маршруты API не должны перехватываться статикой).
2. Для путей, не начинающихся с `/api` и `/metrics`, статика раздаётся через `filesystem`-подобный обработчик: если файл есть в embed FS — отдаём его; иначе возвращаем `index.html` (SPA-fallback для `svelte-spa-router`).
3. Обработчик 404 для `/api` сохраняется — невалидные API-пути по-прежнему дают 404, а не `index.html`.

*Альтернатива (рассмотрена, отклонена):* продолжать раздавать статику отдельным nginx-контейнером. Это оставляет два контейнера и противоречит цели изменения. *Альтернатива:* `github.com/gofiber/contrib/... static` middleware — не даёт полного контроля над SPA-fallback и исключениями путей, поэтому предпочтён собственный обработчик поверх `http.FS`.

### 2. Единый Dockerfile (multi-stage) в `build/Dockerfile`

`build/Dockerfile_front` удаляется, `build/Dockerfile_back` переименовывается в `build/Dockerfile` и переделывается:

- **stage frontend-builder** (`oven/bun:1-alpine`): `bun install --ignore-scripts` + `bun run build` → `front/dist`.
- **stage go-builder** (`golang:1.26-alpine3.22`): копирует `back/` целиком (контекст — корень репозитория) и `front/dist` в `web/dist`, затем `go build ./cmd/cloudbackend/main.go` с `-ldflags` для `APP_VERSION`. Также сборка goose остаётся в этом слое.
- **final stage** (`alpine:3.22`): копирует бинарник, goose, `migrations/`; создаёт не-root пользователя `appuser`, каталог `/app/data`; `HEALTHCHECK` на `http://localhost:3000/api/health` (остаётся единственный порт); запуск `goose up && ./capuchin`.

*Альтернатива (рассмотрена, отклонена):* собирать статику вне образа и копировать артефакт. Это требует закоммиченных/передаваемых артефактов сборки и усложняет воспроизводимость; multi-stage решает ту же задачу чище.

### 3. Один порт и один сервис в compose.yaml

`deploy/compose.yaml` сокращается до единственного сервиса `capuchin` с одним маппингом `3001:3000`. Удаляется публикация `3002:80` и комментарий про nginx. Остаются: образ `ghcr.io/capuchinapp/capuchin:${APP_VERSION}`, SQLite-окружение, `./data:/app/data`, метки версии, внешняя сеть `sonorusops-network` для обратного прокси.

При этом `app.Get("/")` в `app.go` меняет поведение: вместо редиректа `/` → `/api` корень теперь отдаёт `index.html` (это и есть веб-интерфейс).

### 4. Обновление nginx-конфига

`deploy/nginx_capuchin.conf` упрощается: единственный `location /` проксирует на `http://127.0.0.1:3001` (единый порт). TLS-терминация, security-заголовки и gzip сохраняются. Отдельный `location /api` не нужен — теперь один порт обрабатывает и API, и статику.

### 5. CI/CD: одна сборка вместо двух

`.github/workflows/build.yml` собирает один образ `ghcr.io/capuchinapp/capuchin:${{github.ref_name}}` из корня репозитория с `-f build/Dockerfile --build-arg APP_VERSION=...` и пушит его. Шаги сборки фронтенда и пуша второго образа удаляются.

*Альтернатива (рассмотрена, отклонена):* собирать фронтенд отдельным job'ом и класть артефакты в registry перед сборкой образа. Не даёт преимуществ над multi-stage и добавляет шаги и задержки.

### 6. `getBaseUrl()` во фронтенде

Бранч «localhost, port - 1» становится мёртвым (порт теперь один). Он удаляется: в production и на localhost API всегда same-origin `/api`. Значение `VITE_API_BASE_URL=auto` в production-сборке сохраняется.

## Risks / Trade-offs

- **go:embed ломает локальную сборку без собранного фронтенда** → уровень гарантирует файл-заглушку `web/dist/.gitkeep`; в Docker статика всегда пересобирается в stage. Локальная сборка с реальным UI выполняется через `make` (сначала `front` build, затем `go build`).
- **SPA-fallback может перехватывать несуществующие API-маршруты** → catch-all для статики явно исключает `/api` и `/metrics`; несуществующие API-пути по-прежнему возвращают 404 (обработчик 404 для `/api` сохраняется). Покрывается тестом.
- **Обновление с двух-портовой схемы требует пересоздания контейнера** → переход по `docker compose up -d --force-recreate`; том `./data` сохраняется, данные миграций и БД не теряются.
- **Потеря nginx-контейнера = потеря статической кэш-настройки** → во Go-обработчике задаются `Cache-Control` для статики; внешний nginx-прокси остаётся и для gzip, и для TLS.
- **Два процесса в один Dockerfile (goose + app) в одном не-root пользователе** → сохраняется текущая схема единого процесса-контейнера (`sh -c "goose up && ./capuchin"`), уже проверенная на практике.

## Migration Plan

1. Добавить embed-раздачу статики в бэкенд с SPA-fallback (с заглушкой `web/dist/.gitkeep`) и тест на исключения `/api`, `/metrics` и отдачу `index.html`.
2. Убрать редирект `/` → `/api`; удалить dead-code ветку `port - 1` в `getBaseUrl()`.
3. Переработать `build/Dockerfile`, удалить `build/Dockerfile_front`.
4. Сократить `deploy/compose.yaml` до одного сервиса и одного порта.
5. Обновить `deploy/nginx_capuchin.conf` на единственный `location /`.
6. Переписать `.github/workflows/build.yml` на один образ.
7. Обновить README: убрать blue-green, описать single-container развёртывание и обновление.

Развёртывание: `docker compose up -d --force-recreate`. Откат: вернуть предыдущий тег образа в том же сервисе, данные в `./data` не затрагиваются. Внешний nginx-конфиг в откате также возвращается к двух-портовой схеме.
